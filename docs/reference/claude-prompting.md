# Prompting Claude

Reference for writing eitri's prompts (`CLAUDE.md`, `.claude/rules/`, the `design-model` skill, subagent briefs, the render-reading instruction) for the Claude models current on 2026-10-29. Pages cited below were fetched that day; none states a revision date unless noted.

## Models and controls

- Lineup: Opus 5.5 (`claude-opus-5-5`) is the suggested start; Fable 5.1 (`claude-fable-5-1`) is for "demanding reasoning and long-horizon agentic work"; Sonnet 5.5 and Haiku 5.5 are faster. All take image input, with 1M context, 128K output and a June 2026 knowledge cutoff ([models overview](https://platform.claude.com/docs/en/about-claude/models/overview)).
- Thinking is always on in Opus 5.5 and Fable 5.1, so **effort** is the main control ([best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#leverage-thinking-and-interleaved-thinking-capabilities)). The API default is `medium` on Opus 5.5 and Haiku 5.5 and `high` on Sonnet 5.5 ([Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5#calibrate-effort), [Haiku 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-haiku-5-5#use-effort-to-control-thinking), [Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5#calibrate-effort)). Claude Code defaults Opus 5.5, Sonnet 5.5 and Haiku 5.5 to `medium` ([Claude Code best practices](https://code.claude.com/docs/en/best-practices#change-the-model-and-effort)).
- Level names don't mean the same amount of thinking across models, so re-test levels after a model change. Opus 5.5 at `medium` matches or beats Opus 5 at `high` on coding ([Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5#calibrate-effort)). Haiku 5.5 is the first Haiku with effort levels ([Haiku 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-haiku-5-5#use-effort-to-control-thinking)).
- To get less thinking, lower effort, which works "more reliably than prompt instructions do" ([Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5#calibrate-effort)). On Sonnet 5.5 at `medium` and above, asking it to think less "doesn't reliably reduce its thinking" ([Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5#calibrate-effort)); on Haiku 5.5, telling it to answer directly "didn't stop it from thinking" ([Haiku 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-haiku-5-5#use-effort-to-control-thinking)).
- In Claude Code, effort can be set per session (`/effort`), per skill (`effort` frontmatter, which applies "for the rest of the current turn") ([skills](https://code.claude.com/docs/en/skills#frontmatter-reference)), and per subagent (`effort` field) ([subagents](https://code.claude.com/docs/en/sub-agents#choose-an-effort-level)). `ultrathink` in one prompt asks for deeper reasoning on that turn only ([Claude Code best practices](https://code.claude.com/docs/en/best-practices#change-the-model-and-effort)).
- Opus 5 prompts remain "a reasonable starting point" for Opus 5.5, Sonnet 5 prompts for Sonnet 5.5, and Haiku 4.5 prompts "should perform well" on Haiku 5.5 ([Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5), [Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5), [Haiku 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-haiku-5-5)).

## What changed from Claude 4.x

- **Forceful wording overtriggers.** Starting with Opus 4.5 and 4.6, "CRITICAL: You MUST use this tool when..." should become "Use this tool when..." ([best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#tool-usage)). Claude Code now lists "Add IMPORTANT or ALL CAPS" as advice to stop: "Current ones follow a plainly worded line, and piling on emphasis mostly makes Claude over-apply the rule." A line that can't bend becomes a hook or deny rule; a line lost in a long file means the file needs to be shorter ([Claude Code best practices](https://code.claude.com/docs/en/best-practices#what-you-can-stop-doing)). Leftover hedges ("try to", "if possible") read as permission to under-deliver (`claude-api` skill `shared/prompt-audit.md`, read 2026-10-23; not re-read).
- **Literal reading.** Opus 4.8 and Sonnet 5 don't generalize an instruction "from one item to another" or infer requests you didn't make, so state the scope ("every section, not just the first") ([Sonnet 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5#more-literal-instruction-following)). Opus 5 may follow "only report high-severity issues" literally and report less ([Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5#capability-improvements)). The 5.5 pages say nothing new on literalism; that it carries over from 5 is inference from the "starting point" lines above. Fable 5 steers with one brief instruction instead of a list of cases ([Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5#strong-instruction-following)). Claude Code: Claude "tends to read a request conservatively"; `be ambitious` still widens scope ([Claude Code best practices](https://code.claude.com/docs/en/best-practices#write-a-specific-prompt)).
- **Reasoning stays in thinking.** Prompts or skills that ask Opus 5/5.5, Fable 5/5.1 or Sonnet 5.5 to write out their reasoning "might be declined" (`reasoning_extraction`). Asking for "a short explanation of the answer or a summary of the actions taken" is fine ([Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5#safeguard-refusals), [Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5#safeguard-refusals)). `think step by step`, `think hard` and `be thorough` are "ordinary prompt text" that nudges within the effort setting, not keywords that raise it ([Claude Code best practices](https://code.claude.com/docs/en/best-practices#what-you-can-stop-doing)).
- **Verification prompts over-apply.** Opus 5 checks its own work unprompted, and instructions like "use a subagent to verify" cause over-verification; remove them ([Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5#task-scope-and-over-verification)). Sonnet 5.5 at `low` and Haiku 5.5 at `low` and `medium` sometimes report a change done without a check; both pages give the same "run a real check" paragraph ([Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5#verification-on-coding-tasks), [Haiku 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-haiku-5-5#tell-coding-agents-to-verify-their-changes)).
- **Keep-going lines over-work.** "Tell Claude to keep going, loop until done, don't be lazy" is advice to stop: such lines "are more likely to cause over-work than fix a stall". A check to pass is still worth giving ([Claude Code best practices](https://code.claude.com/docs/en/best-practices#what-you-can-stop-doing)).
- **Scope creep.** Opus 5 can widen a task ([Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5#task-scope-and-over-verification)). Sonnet 5.5 adds tests, docs and files unasked at every effort, and at `xhigh` and `max` starts its own review rounds, sometimes with reviewer subagents; its page gives a "When the work... is done and checked, stop and report" paragraph ([Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5#steer-initiative-and-scope)). Fable 5.1 fixes nearby code ([Fable 5.1](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1#keep-changes-and-tests-to-what-the-task-asks-for)).
- **Early stops.** Unattended Opus 5.5 runs can end a turn with a progress report instead of a tool call; it responds to instructions that name the specific stops to avoid ([Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5#unattended-agentic-runs)). Sonnet 5.5 at `low` and `medium` checks in before a coding task is done ([Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5#steer-initiative-and-scope)). Haiku 5.5 stops early with a long agent prompt at `low` ([Haiku 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-haiku-5-5#prevent-early-stopping-in-long-agent-prompts)).
- **Formatting and updates flipped.** Fable 5.1 under-formats, so drop anti-formatting rules ([Fable 5.1](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1#formatting-in-chat)). Remove lines like "hold all findings for the final response" ([Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5#user-facing-progress-updates)). Opus 5 runs long in replies and in files it writes ([Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5#written-deliverable-length)).
- **Vision improved.** Opus 5.5 reads charts, diagrams and position-dependent meaning (which boxes an arrow joins, what changed between two diagrams) better than Opus 5, so re-test vision scaffolding built for older models ([Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5#tools-for-complex-visual-inputs)).
- **API changes.** Prefill returns a 400 from Claude 4.6 on, and `budget_tokens` returns a 400 from Claude 4.7 on ([best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#migration-considerations)).

## General guidance

- Be clear and direct. Test: would a colleague with minimal context follow the prompt? ([best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#be-clear-and-direct)). Give the reason as well as the rule, since "Claude can generalize from the explanation" ([best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#add-context-to-improve-performance); [Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5#give-the-reason-not-only-the-request)). Conflict: Claude Code's skills page says to "state what to do rather than narrating how or why" in a skill body ([skills](https://code.claude.com/docs/en/skills#types-of-skill-content)). Agent Skills reconciles them: explain why where the agent must use judgment, and be prescriptive where the task is fragile ([Agent Skills best practices](https://agentskills.io/skill-creation/best-practices)).
- Examples: 3–5, relevant and diverse, wrapped in `<example>` tags ([best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#use-examples-effectively)). The model copies their length, tone and structure, so one gold example over-anchors (`claude-api` skill `shared/prompt-audit.md`, read 2026-10-23). Prefer "diverse, canonical examples" to a "laundry list of edge cases" ([Anthropic engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents), 2025-09-29).
- Structure: use XML tags when a prompt mixes instructions, context and inputs ([best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#structure-prompts-with-xml-tags)). Put long data first and the question last, which gave up to 30% better answers in tests ([best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#long-context-prompting)).
- Positive vs negative: say what to do, not what to avoid, and match the prompt's own style to the output you want ([best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#control-the-format-of-responses)). Exception: Opus 5.5 responds better to a list of the specific patterns to avoid than to "avoid a generic look" ([Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5#frontend-design-defaults)).
- Brevity: a short instruction ("Lead with the outcome... be selective about what you include") works as well as listing each verbose pattern ([Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5#strong-instruction-following)).
- Actions: "Change this function" gets an edit, while "can you suggest changes" may get only suggestions ([best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#tool-usage)). Parallel tool calls are the default and can be pushed to about 100% with a short instruction ([best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#optimize-parallel-tool-calling)).
- Long tasks: keep state in files and git (a structured tests file, free-text progress notes) ([best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#state-management-best-practices)). Having the model check each progress claim against a tool result "nearly eliminated fabricated status reports" ([Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5#ground-progress-claims-during-long-runs)). Ask for evidence, "the command it ran and its output, or the screenshot" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices#give-claude-a-check-to-run)).

## Standing instructions: CLAUDE.md, rules, skills

- Claude Code sorts every instruction into two kinds: non-deterministic (prompt, CLAUDE.md, skills; Claude decides) and deterministic (hooks, deny rules, managed settings; the harness enforces). "Most of the time, you want Claude to decide." "If you keep adding emphasis to a `CLAUDE.md` line and Claude still misses it, that's a sign the line belongs in a hook", and hooks for mere preferences should go ([Claude Code best practices](https://code.claude.com/docs/en/best-practices#deterministic-and-non-deterministic-instructions)).
- CLAUDE.md is "context, not enforced configuration". It arrives as a user message after the system prompt. Write rules concrete enough to verify, keep each file under 200 lines, group them under headers, and remove contradictions, since Claude "may pick one arbitrarily" ([memory](https://code.claude.com/docs/en/memory#write-effective-instructions)). Conflict: the features overview says that on conflict "Claude uses judgment to reconcile them" ([features overview](https://code.claude.com/docs/en/features-overview#understand-how-features-layer)). A user rule and a project rule don't override each other; "Claude may follow either one" ([memory](https://code.claude.com/docs/en/memory#user-level-rules)).
- `/doctor prompt-audit` (v2.1.283 or later) checks CLAUDE.md, rules, skills, subagents and output styles for text written for older models, references to missing files or commands, and files that contradict each other, and proposes edits ([memory](https://code.claude.com/docs/en/memory#audit-your-instruction-files)).
- A path-scoped rule loads when Claude uses Read, Write or Edit on a matching file, or `cat`/`head` on one file ([memory](https://code.claude.com/docs/en/memory#path-specific-rules)). Whether a rule triggered by a Write is in context before that Write's content is composed: not found (the `InstructionsLoaded` hook reports `path_glob_match` loads but not their timing ([hooks](https://code.claude.com/docs/en/hooks#instructionsloaded))).
- Skills: the `description` says what the skill does and when to use it, in the third person ([skill authoring](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices#writing-effective-descriptions)). Put the key use case first, because the listing cuts it at 1,536 characters. Keep `SKILL.md` under 500 lines ([skills](https://code.claude.com/docs/en/skills#frontmatter-reference)). Detail is in `claude-code-skills.md`.
- A loaded skill stays in context, is not re-read, and after compaction keeps only its first 5,000 tokens. Write its guidance as standing instructions ("Run the tests after every edit") and put the most important lines first ([skills](https://code.claude.com/docs/en/skills#claude-stops-following-a-skill)).
- Match specificity to fragility. Use exact steps only where one sequence is safe, and run a validator, fix and repeat, with "verbose" error messages ([skill authoring](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices#set-appropriate-degrees-of-freedom)). Skills written for prior models are "often too prescriptive" for Fable 5 and "can degrade output quality" ([Fable 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5#recommended-scaffolding-changes)).
- Over-applied or ignored: piles of MUST/NEVER; prohibition lists, which "can anchor it toward" the failure; "the recency trap", where one session's stumble becomes a permanent rule (`claude-api` skill `shared/prompt-audit.md`, read 2026-10-23; not re-read). Instructions that don't apply to the current task get followed anyway and waste steps ([Agent Skills best practices](https://agentskills.io/skill-creation/best-practices#refine-with-real-execution)).

## CLAUDE.md

- Scope: facts Claude should hold in every session, such as build commands, conventions, layout and "always do X" rules. A multi-step procedure, or anything that matters for only part of the codebase, goes in a skill or a path-scoped rule ([memory](https://code.claude.com/docs/en/memory#when-to-add-to-claude-md)). "A 30-line procedure in CLAUDE.md" is a named anti-pattern, and CLAUDE.md can serve as "an index pointing to other files" ([Anthropic blog](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more), 2026-06-18). The documented pairing is the always-on rule in CLAUDE.md and the full material in a skill ([features overview](https://code.claude.com/docs/en/features-overview#combine-features)).
- "Every line in it takes a little of Claude's attention on *every* task." Keep: the exact check commands, places where the code misleads, decisions that aren't in the repo, and anything corrected twice. Test before writing a line: "Could it find this by reading the code? Would it actually go and look? If both are yes, leave it out." "Describe your architecture and file layout" is advice to stop ([Claude Code best practices](https://code.claude.com/docs/en/best-practices#keep-claude-md-short), [#tell-claude-what-it-cant-see](https://code.claude.com/docs/en/best-practices#tell-claude-what-it-cant-see)). Also leave out history and rules nobody follows: "outdated instructions are worse than none" ([Claude support](https://support.claude.com/en/articles/14553240-give-claude-context-claude-md-and-better-prompts), 2026-04-15). `/doctor` proposes cuts of derivable content and keeps "pitfalls, rationale, and conventions that differ from tool defaults" ([memory](https://code.claude.com/docs/en/memory#my-claude-md-is-too-large)).
- Keep "never do X" rules in the root file: the `/doctor` trim prompt says to "never move a 'never do X' rule into a lazy skill where it might not be loaded when it matters" and "When unsure, keep it" (Claude Code v2.1.314 binary strings, no URL).
- Add a line when Claude gets a convention or command wrong twice ([features overview](https://code.claude.com/docs/en/features-overview#build-your-setup-over-time)). A line like "Always typecheck before you finish" "works most of the time, not every time"; enforcement is a Stop hook ([Claude Code best practices](https://code.claude.com/docs/en/best-practices#keep-claude-md-short)).
- Size limits: a CLAUDE.md loaded at launch is read whole up to 4 MiB. Startup and `/status` warn when a file passes the recommended length or all files together pass a combined limit. On-demand files (nested CLAUDE.md, path-scoped rules) are cut at 40,000 characters on a 200K context or 150,000 on a 1M context (Claude after 4.6), from v2.1.309 ([memory](https://code.claude.com/docs/en/memory#claude-ignores-the-end-of-my-subdirectory-claude-md)). `@path` imports don't reduce context cost ([memory](https://code.claude.com/docs/en/memory#write-effective-instructions)).
- A `CLAUDE.md` in a subdirectory loads once Claude reads, writes or edits a file there, `cat` and `head` included ([memory](https://code.claude.com/docs/en/memory#how-claude-md-files-load)). `claudeMdExcludes` skips files by absolute-path glob, from any settings layer ([memory](https://code.claude.com/docs/en/memory#exclude-specific-claude-md-files)). In eitri, `lib/BOSL2/CLAUDE.md` holds BOSL2's contributor rules, such as docsgen comment blocks on every public function and a closing vim modeline (BOSL2 `CLAUDE.md:93`, `:122`), and loads when Claude reads a BOSL2 file.
- After compaction, the project-root CLAUDE.md and unscoped rules are re-read from disk, while nested CLAUDE.md files and path-scoped rules return only when a matching file is touched again. A rule that must survive compaction goes in the root CLAUDE.md or loses its `paths:` ([context window](https://code.claude.com/docs/en/context-window#what-survives-compaction)).
- Block-level HTML comments are stripped before CLAUDE.md reaches Claude, so maintainer notes cost no context ([memory](https://code.claude.com/docs/en/memory#how-claude-md-files-load)).
- For eitri, these findings put the step-by-step loop in the skill. CLAUDE.md keeps the recipe commands, the rules, and "never hand over a model whose latest renders you haven't read"; `design-model` keeps the loop and the hand-over list (inference from the scope findings above).

## Delegation

- A subagent starts fresh. It sees the brief plus every CLAUDE.md level and project rules, but Explore and Plan skip those; for them a subdirectory CLAUDE.md and matching path-scoped rules still load when they work with files there. A custom subagent can skip CLAUDE.md with `omitClaudeMd: true` ([subagents](https://code.claude.com/docs/en/sub-agents#what-loads-at-startup)). A rule that must reach Explore or Plan goes in the brief.
- A brief needs "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries"; vague briefs led subagents to duplicate work and leave gaps ([Anthropic engineering](https://www.anthropic.com/engineering/multi-agent-research-system), 2025-06-13). Ask for short summaries back ([Claude Code best practices](https://code.claude.com/docs/en/best-practices#know-what-subagents-cost)).
- "Delegate to a subagent for a better answer" is advice to stop: a subagent is the same or a smaller model, and a fresh one first has to gather context, so it can be slower. Subagents pay off for parallel work, noisy output, independent review, and a reduced tool set ([Claude Code best practices](https://code.claude.com/docs/en/best-practices#know-what-subagents-cost)). Opus 5's damping text: delegate only "large tasks that are genuinely independent and parallelizable", not work "you can finish yourself in a handful of tool calls" ([Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5#controlling-subagent-spawning)).
- Reviewers: "A reviewer that's asked to find problems will always find *something*", so ask it to report gaps that affect correctness and skip style ([Claude Code best practices](https://code.claude.com/docs/en/best-practices#review-against-your-spec)). A separate skeptical evaluator was "far more tractable" than self-critique, but became "unnecessary overhead" for tasks within Opus 4.6's solo capability ([Anthropic engineering](https://www.anthropic.com/engineering/harness-design-long-running-apps), 2026-03-24). Conflict: Opus 5's damping text says not to use subagents to verify its own work ([Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5#controlling-subagent-spawning)).

## Vision: checking renders

- Size: Claude 4.7 and later downscale images past 2,576 px on the long edge or 4,784 visual tokens. Cost is ⌈w/28⌉ × ⌈h/28⌉ tokens, so a 1000 × 1000 image costs 1,296. Above 20 images in one request, a stricter limit applies to every image, earlier turns included; images 2000 px or less on each side stay under it ([vision](https://platform.claude.com/docs/en/build-with-claude/vision#request-limits); read 2026-10-23, not re-read).
- Claude Code's Read downscales large images. For fine detail, crop the region and read the crop ([tools reference](https://code.claude.com/docs/en/tools-reference)); on this Mac that is `sips`, since ImageMagick isn't installed (checked 2026-10-23). Whether Claude Code enforces the 2000 px limit for many-image requests: not found.
- Put images before the text, and label several images ("Image 1:", "Image 2:") so the prompt can name them ([vision](https://platform.claude.com/docs/en/build-with-claude/vision#multiple-images)).
- Weak spots: low-quality, rotated or under-200 px images; coordinates and localization are "approximate"; counts are "approximate... especially with large numbers of small objects". Don't use it "for tasks requiring perfect precision" without oversight ([vision](https://platform.claude.com/docs/en/build-with-claude/vision#limitations)).
- Two things still add accuracy on dense inputs: higher resolution, "most of all for... technical drawings", and tools to crop, zoom and measure. Without tools, more effort helps technical drawings but "does little for charts" ([Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5#tools-for-complex-visual-inputs)). On Sonnet 5.5, crop tools help technical drawings only from `high` effort up ([Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5#tools-for-complex-visual-inputs)). A zoom tool raised Fable 5's chart accuracy from 29% to 73%, at about 12× the cost per question; an agent that can run code "will typically write its own crop-and-magnify script" ([crop tool cookbook](https://platform.claude.com/cookbook/multimodal-crop-tool)).
- Observations before conclusions: the closest current guidance is "quote relevant parts... first" for long documents ([best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#long-context-prompting)) and a screenshot next to the mockup as a check ([Claude Code best practices](https://code.claude.com/docs/en/best-practices#give-claude-a-check-to-run)). An image-specific rule: not found. Conflict: the [vision best-practices cookbook](https://platform.claude.com/cookbook/multimodal-best-practices-for-vision) asks for step-by-step reasoning in `<thinking>` tags, which the current models may decline (see above).
- Numbers come from code: put data in files or tool results and arithmetic in code (`claude-api` skill `shared/prompt-audit.md`, read 2026-10-23). Images can't give exact sizes, positions or counts (the vision weak spots above).

## Recommendations for eitri

- **Keep CLAUDE.md short and current.** CLAUDE.md holds the commands and rules and points to `design-model` for the loop (see the CLAUDE.md section above). If one rule keeps being skipped, shorten the file or turn the rule into a hook; don't add emphasis (Claude Code best practices).
- **Enforce the loop with hooks, not wording.** The planned `PostToolUse` compile hook fits. If Claude hands over without a passing `just check`, add a Stop hook that runs it rather than stronger text. A Stop hook that blocks eight stops in a row with no tool call between them is overridden ([Claude Code best practices](https://code.claude.com/docs/en/best-practices#enforce-the-check-with-a-stop-hook)).
- **Keep `paths:` on `.claude/rules/openscad.md`.** Explore and Plan skip unconditional rules but load path-scoped ones when they open a matching file ([subagents](https://code.claude.com/docs/en/sub-agents#what-loads-at-startup)). If a new model's first draft misses a convention, have `design-model` open the rule before the first Write of a new `.scad` file (inference, from the rule-timing gap above).
- **Write `design-model` short and standing.** Put the loop and the per-view checklist first. Phrase lines for the whole task ("after every change") and state scope ("every view", "every parameter set"). Leave thresholds to `just check`. Optionally test `effort: high`, since effort helps on technical drawings (skills and vision findings).
- **Render square views at 1000 to about 1900 px.** A 1000 px view costs 1,296 tokens; above about 1,930 px a square passes the 4,784-token cap and gets downscaled. Each iteration adds five images, so if earlier renders stay in the resent history, a fifth iteration passes 20 images, and any image over 2000 px is then rejected (arithmetic from the vision limits; that Claude Code resends earlier images is inference).
- **Render-reading instruction.** Read the five PNGs first, each introduced by its name ("Image 1: iso" and so on). Then report one short line per view on named features: cell outline, AOS at the center, flat back on z = 0, missing or floating pieces, and match to the reference images. Give a verdict after the lines. Ask for observations, not "reasoning" or "thinking", which may be declined.
- **Take sizes from the check JSON and other numbers from the `.scad`.** `just check` prints only `{model,size,min,max}` and fails on a non-manifold mesh, a min z other than 0, or a size over 256 × 256 × 260 mm (`justfile`, read 2026-10-23). Take counts, wall widths and positions from the `.scad` parameters, not a render (counting 18 cells off a render is the kind of count vision gets approximately; inference). Renders confirm meaning only, which matches CLAUDE.md's "numbers vs images" rule (vision weak spots).
- **Crop instead of guessing.** When a seat ledge or thin wall matters, crop that region of a render and read the crop, or check its size in code (tools reference, crop tool).
- **Subagent briefs.** Give the objective, the output format, which files and tools to use, and what is out of scope. Restate "never invent a dimension" and the units for Explore and Plan. Keep the build-render loop in the main session, since it is short and shares context. If a reviewer is used at hand-over, give it only the renders, the reference images and the criteria, and limit it to requirement gaps (delegation findings).
- **Hand-over cites evidence.** Quote the `just check` JSON and name the renders read, alongside the 3MF, orientation and what to check on the print (progress-claims and evidence findings).
- **Don't add** IMPORTANT or capitals, "think step by step", "be thorough", "double-check", "keep going", "don't be lazy", "hold findings", or anti-formatting rules. If quality on a model needs more depth, raise effort instead (changes from 4.x).
